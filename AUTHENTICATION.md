# Authentication setup (local only)

No deployment was performed. The app no longer trusts Sites/ChatGPT identity headers or mock login. Existing employee IDs, task assignments, profiles and applications are preserved. Existing `members.user_id` values are legacy metadata and are never used for authentication.

1. Use Node 22.13+ and the existing locked dependencies. Copy `.dev.vars.example` to `.dev.vars` (ignored). Set `AUTH_ORIGIN` to the exact browser origin including port, normally `http://localhost:5173`. `127.0.0.1` and `localhost` are different origins. For `npm start`, use its printed origin and restart after configuration changes.
2. Generate a one-time setup token with `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"` and put it in `AUTH_SETUP_TOKEN`. This token is not the admin password. Never commit real tokens or passwords.
3. Build with `npm run build`. For a new database only, initialize the original tables using `node --import ./scripts/sites-env.mjs node_modules/wrangler/bin/wrangler.js d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file migration-guide/schema-fresh.sql`. Skip this step for an existing database. Back up valuable local data before applying migrations.
4. Apply the additive auth migration exactly once: `node --import ./scripts/sites-env.mjs node_modules/wrangler/bin/wrangler.js d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0005_password_auth.sql`. Do not replay the original five migrations on a database initialized using schema-fresh.sql. The fresh SQL intentionally contains only the original application tables.
5. Start `npm run dev`, open `/setup`, enter the setup token and choose your own admin password. The administrator email is `syedmauz20@gmail.com`. The database permits only one admin; setup cannot overwrite it, including concurrent attempts. After successful setup, remove AUTH_SETUP_TOKEN and restart the server. Sign in at `/login`.
6. In **Employee Logins**, create an employee using name, email and a temporary password (12-128 characters). Share it privately; no email is sent. For existing employees, use **Reset password** to initialize their new login without changing their ID or tasks. The employee must change the temporary password before any workspace API or dashboard access. Password changes sign out all sessions. Reset and disable revoke sessions; enable never revives a revoked session. Disabled accounts cannot sign in.

Password hashes use independently salted scrypt (N=32768, r=8, p=3), following the [OWASP password storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). Passwords are never returned by account APIs. Admins can set a new temporary password but cannot retrieve an existing one. Neither credentials nor session tokens are stored in localStorage.

Sessions use 256-bit random tokens with only SHA-256 digests stored in D1, an absolute eight-hour expiration, and host-only HttpOnly / SameSite=Strict cookies. HTTPS origins add Secure; HTTP is permitted only on localhost or 127.0.0.1. All mutating authentication and workspace requests validate Origin. Roles and active status are checked on the server for each request, with task and employee data scoped to the signed-in employee. Public website/application intake remains public.

Login/setup/password change attempts use atomic D1 counters across instances: eight attempts per account and thirty per IP per fixed 15-minute window. Cloudflare's trusted `CF-Connecting-IP` supplies the IP; environments without that header share the conservative IP bucket. Do not expose this Worker through a proxy that accepts spoofed CF-Connecting-IP from clients. Sessions and counters are pruned during authentication requests. Expired records grant no access even before cleanup.

Future hosting must supply the DB and BUCKET bindings, an HTTPS AUTH_ORIGIN and server-side setup secret through its secret configuration. The app's login replaces application identity; any independent host-level audience restrictions still apply. No hosting changes are included here. Keep local secret/state directories out of source archives. Database-only admin recovery requires an operator-controlled password hash replacement and session revocation; there is no public password recovery endpoint.

Checks: `node node_modules/typescript/bin/tsc --noEmit`, `node --test tests/*.test.mjs tests/*.test.cjs`, and `npm run build`.

## Administrator settings and completed setup

After an administrator exists, `/login` hides First administrator setup. `/setup` redirects anonymous visitors and employees to `/login`, and a signed-in administrator to `/dashboard`. Direct setup API requests return 409 once an admin exists, independent of the setup token or rate counters. The single-admin database constraint also prevents concurrent creation. You can remove AUTH_SETUP_TOKEN after setup.

The admin dashboard has **My Account / Settings** for display name, full name, job title, phone, time zone and bio. Profile values persist in `account_profiles` and the display name is used in the dashboard and subsequent activity. Email is read-only because no verified email-change service is configured; API requests cannot modify email or role. Password change verifies the current password, updates the hash and revokes all account sessions atomically, then requires login again.

Apply `drizzle/0006_account_profiles.sql` exactly once after migration 0005 for each database. It adds a profile table without changing existing accounts, hashes or application data. For the existing local database, `node scripts/apply-account-profile-local.mjs` checks whether that table already exists and applies only migration 0006 when needed. It never resets the database or modifies account credentials. For a new database, apply 0005 and 0006 after the original schema initialization described above.
